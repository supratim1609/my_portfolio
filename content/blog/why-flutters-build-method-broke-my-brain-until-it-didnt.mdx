Until I added a counter.

Just a counter.

@override

    body: Center(  
      child: Column(  
        mainAxisAlignment: MainAxisAlignment.center,

Every click? build().  
Change a variable? build().  
Look at it funny? build() again.

### **Why is it rebuilding? I didn’t _ask_ for this!**

My console was filled with print()s screaming for help. My stateful widget was acting like a clingy ex — couldn’t stop coming back.

But here’s what I _didn’t_ know then:

> **Flutter rebuilds the widget tree to reflect the latest state. That’s not a bug — it’s how Flutter works.**

When you call setState(), you're telling Flutter:

> _“Hey, something changed. Rebuild this widget so the UI can reflect the latest version of reality.”_

### **Rebuild Isn’t Evil — You Just Gotta Know What You’re Doing**

Let’s break it down:

#### Flutter’s Widget Lifecycle (Simplified)

*   **Widgets are immutable.**  
    Once created, they don’t change.
*   **When state changes, Flutter rebuilds the affected widgets.**  
    Not the whole app, just the parts depending on the changed state.
*   **If you’re not careful, everything might rebuild.**

#### Here’s What _Not_ to Do

Widget build(BuildContext context) &#123;  
  return Column(  
    children: \[  
      Text('$counter'),  
      MyHeavyWidget(), // rebuilds every time unnecessarily  
    \],  
  );  
&#125;

You just made MyHeavyWidget() rebuild **every single time**, even if it has nothing to do with counter.

### What Helped Me Chill

#### Use const Wisely

If a widget doesn’t change, tell Flutter that. It won’t rebuild it.

const MyHeavyWidget() // won't rebuild!

You save time, memory, and probably your sanity.

### Extract Widgets (Seriously, Do It)

Break things down like modular code. Smaller widgets = better control.

class CounterText extends StatelessWidget &#123;  
  final int counter;  
  const CounterText(this.counter, &#123;super.key&#125;);  
  
  @override  
  Widget build(BuildContext context) &#123;  
    print("⏱️ CounterText rebuilt");  
    return Text('$counter');  
  &#125;  
&#125;

Now your layout becomes:

Column(  
  children: \[  
    CounterText(counter), // only this depends on the counter  
    const MyHeavyWidget(), // completely untouched  
  \],  
)

### Use Keys When Things Get Weird

#### **First off — what _are_ keys?**

A Key in Flutter is like a name tag for widgets. It helps Flutter keep track of widgets between rebuilds, especially in dynamic or complex UIs like lists, forms, or animations.

> _Think of it like this: Flutter doesn’t remember widgets — it remembers their_ **_position_** _in the widget tree. So when the tree changes (say, you reorder or delete an item), Flutter can get confused and accidentally reuse or rebuild the wrong widget. Keys fix that._

Example:

ListView.builder(  
  itemCount: myItems.length,  
  itemBuilder: (\_, i) => MyItemWidget(  
    key: ValueKey(myItems\[i\].id),  
    item: myItems\[i\],  
  ),  
);

So if you’re seeing weird bugs like reused form fields, animations glitching, or state behaving unexpectedly in a list — **check your keys.**

### Common Mistakes I Made

*   Wrapping everything in setState(), like a desperate catch-all.
*   Ignoring const, like it was optional.
*   Keeping too much logic in the build() method. (Don’t.)
*   Forgetting about the widget lifecycle. (Everything’s a rebuild candidate!)
